# QUALITY_GATES
## Автоматические проверки и критерии приёмки

**Версия:** 1.2 · **Назначение:** исполняемая модель принуждения стандарта `ENGINEERING_PRINCIPLES.md`. Стандарт исполняется конвейером, а не инструкциями в промпте агента. Часть правил — процессные (исполняются ревью и артефактами процесса); они явно помечены, их доля публикуется как метрика зрелости (§6).

---

## 1. Модель принуждения: четыре уровня

Стандарт исполняется эшелонированно — чем раньше поймано нарушение, тем дешевле исправление:

| Уровень | Механизм | Что ловит | Задержка |
|---|---|---|---|
| **L0. Периметр** | Настройки хостинга: branch protection, запрет force-push, обязательные проверки, CODEOWNERS на инфраструктуру стандарта (§1.5) | Гарантия, что L1–L3 нельзя обойти пушем в main или галочкой в настройках | постоянно |
| **L1. Инструкции** | `AGENTS.md` / `CONTRIBUTING.md` в корне репозитория, ссылающиеся на `AI_AGENT_RULES.md`; PR-шаблон; шаблон задачи | Направление работы агента, границы задачи | до кода |
| **L2. Pre-commit** | Хуки: формат, быстрый линт, скан секретов | Ошибки форматирования, секреты, «забыл линт». Хуки обходятся (`--no-verify`) — всё критичное дублируется в L3 | секунды |
| **L3. PR-гейты** | CI на каждый PR: сборка-матрица, линт/типы/анализ, юнит- и интеграционные тесты, аудит зависимостей, арх-тесты, api-diff, coverage-диф | Все механически проверяемые требования | минуты |
| **L4. Ночные/фоновые** | Фаззинг, глубокий статический анализ, бенчмарки, нагрузочные тесты утечек, аудит новых CVE в существующих версиях | Долгие и стохастические проверки | часы |

**Ключевое правило:** любое правило стандарта, которое можно проверить автоматом, обязано иметь гейт, **если только** правило сознательно не отнесено к процессным с записанным обоснованием (перечень — §5 и итоговая таблица `ENGINEERING_PRINCIPLES.md`). «Не механическое» должно быть явным решением, а не умолчанием.

## 1.5. L0. Периметр репозитория (обязательные настройки хостинга)

Механическое принуждение существует, только если его нельзя выключить изнутри репозитория. Для К1/К2 обязательны:

1. **Защита основной ветки:** прямой push запрещён; изменения — только через PR с обязательными проверками (required status checks); force-push и удаление ветки — запрещены.
2. **CODEOWNERS на инфраструктуру стандарта** (защищённые пути): конфигурации CI (`workflows/`), конфиги линтеров/типов/анализаторов, файлы базовой линии храповика, `EXCEPTIONS.md`, `REPO_CLASS`, `AGENTS.md`, PR-шаблон, `CODEOWNERS`, манифест критичных модулей. Владелец — владелец стандарта.
3. **Ревью — только человек.** Агент не может одобрять PR (ни свой, ни PR другого агента). Для меток `gates-change`/`rule-change`/breaking — CODEOWNERS + минимум один человек-ревьюер. Если в организации допускается ревьюер-агент: другой поставщик/модель, запрет самопроверки, обязательные Q-10/Q-11/Q-12.
4. **Режимы прав агента:** по умолчанию агент создаёт draft-PR; перевод в «ready for review» — после зелёного CI и человеческого действия. Подтверждённое нарушение H6 (фикция верификации) — понижение агента/автора в режим «только draft» до разбора (см. `EXCEPTIONS_POLICY.md` §8).
5. **Запрет админ-обхода** (либо: админ-мердж минус гейты — только как «процессное отступление» с записью и обязательным отложенным прогоном, §6).
6. **Маркировка происхождения:** коммиты агента несут трейлер `AI-Origin: <агент/модель>` — для пост-инцидентного аудита и метрик по субъектам.

Рекомендуемые (не обязательные): подписанные коммиты; canary-маркеры прочтения `AGENTS.md` (1–2 проверяемых поведенческих требования — например, обязательный формат отчёта H9; их отсутствие в PR = L1 не прочитан, бот отклоняет).

**Правило L0:** без выполненного §1.5 стандарт не считается внедрённым (`IMPLEMENTATION_GUIDE.md`, этап 3).

## 2. Классы проектов и строгость

Гейты настраиваются по классу репозитория/модуля (определения классов — `ENGINEERING_PRINCIPLES.md` §0.6):

| Гейт | К1 (критичн./производит.) | К2 (продакшн) | К3 (эксперим.) |
|---|---|---|---|
| Формат/линт/типы | блокирующий | блокирующий | блокирующий (базовый набор) |
| Статический анализ | блокирующий + sanitizers | блокирующий | warning |
| Юнит-тесты | блокирующий | блокирующий | блокирующий |
| Интеграционные тесты | блокирующий | блокирующий | по наличию |
| E2E | блокирующий (дым) | блокирующий (дым) | — |
| Coverage-диф | блокирующий: ≥ 80% (branch) на изменённом коде критичных модулей | блокирующий: ≥ 70% (branch) на изменённых функциях; глобальное покрытие — храповик без блокировки (алерт при дрейфе) | информация |
| Архитектурные тесты | блокирующий | блокирующий | — |
| Аудит CVE | блокирующий (критичные) | блокирующий (критичные), срок для прочих | еженедельный отчёт |
| Скан секретов | блокирующий | блокирующий | блокирующий |
| api-diff | блокирующий | блокирующий для публичного | — |
| Бенчмарки | блокирующие пороги на бюджетных путях | ночные + алерты | — |
| Фаззинг | ночной; цели = точки разбора недоверенных данных (перечень целей фиксируется в репозитории) | ночной (те же цели) | — |

«Базовый набор К3» — определён в `ENGINEERING_PRINCIPLES.md` §0.7 (несущие термины).

## 3. Правило храповика (ratchet)

Для существующих репозиториев «с первого дня ноль нарушений» нереализуемо, поэтому:

1. **Базовая линия** фиксируется при внедрении (снимок текущих нарушений по каждому инструменту: количество на файл/правило).
2. **Запрещён рост**: PR не может увеличить число нарушений любого вида. Может уменьшить.
3. Базовая линия монотонно снижается; целевые уровни — планом внедрения (`IMPLEMENTATION_GUIDE.md`).
4. Снижение базовой линии «сами по себе» (без PR) запрещено — линии меняются только через PR с обоснованием.
5. **Без взаимной компенсации:** рост любого вида нарушений в PR запрещён независимо от снижений; «+5 новых против −6 исправленных старых» не проходит — новая категория нарушений не компенсируется починкой старых.
6. **Базовая линия — защищённый путь:** файлы базовой линии под CODEOWNERS владельца стандарта; изменение baseline и кода — в разных PR (сброс — метка `baseline-reset`); механические перемещения кода (rename/генерация) не пересчитывают baseline вручную — миграцию выполняет инструмент ratchet.
7. **Принуждение к снижению:** L4-джоба «базовая линия по виду нарушений не снижалась N месяцев» — алерт владельцу с обязательным планом.

Формально: `violations(new_code) ≤ violations(base) − improvements`. Инструменты: режим «только новые проблемы» (reviewdog, golangci-lint `--new-from-rev`, ruff `--no-cache` + diff, mypy `--follow-imports=skip` + incremental baseline и т.п.).

## 4. Каталог гейтов

Формат: **ID · проверяет · инструменты (примеры) · критерий прохождения · режим.**

### Q-01 Форматирование
- Проверяет: единообразие формата (не содержательную сложность).
- Инструменты: formatter экосистемы (gofmt, black/ruff format, prettier, rustfmt, clang-format, ktlint).
- Критерий: диф после formatter'а пуст.
- Режим: блокирующий, L2+L3.

### Q-02 Линтер
- Проверяет: идиомы, простые дефекты, домены A/D (A1, A6, B3, D3 частично).
- Инструменты: eslint+plugins, ruff/flake8, golangci-lint, clippy, cppcheck, clang-tidy, detekt, SpotBugs.
- Критерий: ноль новых срабатываний (храповик); конфиг проекта = строгий профиль стандарта. **Метрики сложности (A4):** абсолютные пороги — warning; для функций, *изменённых* в PR, — храповик в blocking-режиме: превышение порога требует явного чекбокса-обоснования в PR-шаблоне (наличие проверяется механически, качество — ревью). Сгенерированный код признаётся по конфигу генерации (§0.7 `ENGINEERING_PRINCIPLES.md`), а не по пометке в шапке файла.
- Режим: блокирующий. Правило «исправляй код, а не предупреждение» (F2): подавление — только точечно с комментарием-ID причины; подсчитывается гейтом Q-11.

### Q-03 Типы
- Проверяет: D1 (контракты в типах), F3.
- Инструменты: tsc `strict`, mypy `strict`, javac `-Xlint`, rustc (по умолчанию), компиляторы в режиме warning-as-error (примеры по экосистеме).
- Критерий: ноль ошибок типов; `any`/`unchecked`-обходы — только с локальными подавлениями (считаются Q-11).
- Режим: блокирующий.

### Q-04 Юнит- и интеграционные тесты
- Проверяет: F1, D6 (матрицы границ), F6 (регрессии).
- Критерий: все зелёные; бюджеты времени на класс тестов (юнит — минуты; интеграция — десятки минут; e2e — настраивается), hang-детектор на каждый класс; flaky — карантин только с владельцем, причиной и сроком, с авто-возвратом в блокирующий режим по истечении.
- Режим: блокирующий, L3.

### Q-05 Покрытие
- Проверяет: F1 — достаточность тестирования критичных модулей.
- Критерий: **диф-политика.** К1: ≥ 80% ветвей на изменённом коде критичных модулей (манифест критичных модулей — защищённый путь, §0.7 `ENGINEERING_PRINCIPLES.md`). К2: ≥ 70% ветвей на изменённых функциях; глобальное покрытие — храповик без блокировки (алерт: > 0,5 п.п. снижения за PR или > 2 п.п. за квартал). К3: информация. Глобальный абсолютный порог — не гейт (поощряет тесты ради процента).
- Режим: блокирующий на диф; глобальный — информационный.

### Q-06 Статический анализ (глубокий)
- Проверяет: домены A/B/D глубже линтера (поток данных, утечки, гонки).
- Инструменты: CodeQL/Semgrep, Infer, clang static analyzer; sanitizers (ASan/UBSan/TSan) на тестовых сборках C/C++/Rust; `go test -race`.
- Критерий: ноль новых находок (храповик); для К1 — ноль находок санитайзеров в тестах безусловно.
- Режим: L3/L4.

### Q-07 Секреты
- Проверяет: G4.
- Инструменты: gitleaks/trufflehog, pre-commit + CI.
- Критерий: ноль находок. **Не подлежит храповику и исключениям**, кроме немедленной ротации+истории-чистки.
- Режим: блокирующий всегда.

### Q-08 Аудит зависимостей
- Проверяет: G3, E5.
- Инструменты: osv-scanner, `npm audit`, `pip-audit`, `cargo audit`, OWASP Dependency-Check; лицензионный скан.
- Критерий: нет критичных CVE; прочие — без роста + срок; lockfile в коммите; новые зависимости — с обоснованием в описании PR.
- Режим: блокирующий (по классу), L3 + еженедельно.

### Q-09 Архитектурные тесты
- Проверяет: E1, E3 (направления зависимостей, циклы), A6 (экспорт изменяемых глобалов — где выразимо).
- Инструменты: ArchUnit, dependency-cruiser, eslint-plugin-boundaries, import-linter, jdeps, go list-скрипты.
- Критерий: граф импортов соответствует декларации в `ARCHITECTURE.md` репозитория; циклов нет.
- Дополнительно: интерфейс/трейт/абстрактный класс с единственной реализацией в *новом* коде К1/К2 — блокируется как спекулятивная абстракция (E2/H2), если не имеет тестовой подмены или пометки стратегической точки в `ARCHITECTURE.md`.
- Режим: блокирующий К1/К2.

### Q-10 API-диф и совместимость
- Проверяет: H3, E4, E7.
- Инструменты: api-diff (Kotlin/Java), rustdoc-json diff, `git diff --stat` по публичным экспортам, protobuf/openapi breaking-детекторы.
- Критерий: изменение публичной поверхности требует раздела «Изменения контрактов» в PR; breaking — второго ревьюера. Метки `api-change`/`breaking` проставляет бот по результатам api-diff, а не автор PR.
- Режим: блокирующий для библиотек/платформ.

### Q-11 Подавления и конфигурации гейтов (guard-гейт)
- Проверяет: H4, F2.
- Критерий: (1) число подавлений в дифе сравнивается с **базовой линией храповика**, а не с числом, заявленным автором PR (самоотчёт — не источник данных для гейта); (2) каждое новое подавление — с комментарием-причиной и действующим ID `EX-…` из `EXCEPTIONS.md` (подавление без валидного EX-ID — красный; механическая связка с реестром); (3) более 3 подавлений на PR — второй ревьюер; (4) диф **эффективной** конфигурации инструментов (распарсенный конфиг, а не список путей) и появление любого нового конфиг-файла инструмента в дереве, включая вложенные конфиги подкаталогов, — метка `gates-change` проставляется принудительно ботом; (5) файлы базовой линии — под CODEOWNERS; изменение baseline и кода — в разных PR (`baseline-reset`).
- Словарь подавлений — версионируемый конфиг гейта со своим тестом-контрактом; минимум: `noqa`, `nolint`, `# type: ignore`, `@ts-ignore`/`@ts-expect-error`/`@ts-nocheck`, `noinspection`, `#[allow]` (включая crate-level), `@SuppressWarnings`, `eslint-disable`, `as any`, `unsafe`, `pytest.mark.skip|xfail|skipif`, `ignore_errors`, per-file-ignores и исключающие пути инструментов.
- Режим: блокирующий.

### Q-12 Изменение эталонов и правил (guard-гейт)
- Проверяет: H8, H5.
- Критерий: диф golden-файлов, формул, таблиц тарифов требует метки `rule-change` (проставляет бот по списку защищённых путей), владельца из CODEOWNERS и второго ревьюера. Файл под несколькими guard-гейтами — метки всех применимых и подпись наивысшего по §5 `EXCEPTIONS_POLICY.md`. Новые golden/snapshot в том же PR, что и изменение кода, — усиленное ревью (агент не назначает собственное поведение оракулом). Рекомендация К1: семантические сигналы (изменение числовых литералов в расчётных модулях).
- Режим: блокирующий.

### Q-13 Бенчмарки и регрессии производительности
- Проверяет: C6, B5, F7.
- Критерий: бюджетные пути — трекинг p50/p99 в ночных прогонах; алерт при > +20% к 7-дневному среднему (порог настраивается). Для PR, затрагивающих бюджетные пути, CI-джоба бенчмарка обязательна; измерения «до/после» — ссылкой на артефакт прогона, а не «числами в описании»; метку `perf` проставляет бот по дифу бюджетных путей.
- Режим: алерт + блокировка только бюджетных путей К1.

### Q-14 Фаззинг
- Проверяет: F5.
- Критерий: ночные цели парсеров; краш = задача с минимальным воспроизводящим входом, который добавляется в юниты (F6) до закрытия. Закрытие задачи без регрессионного теста — только при действующем отступлении E-C «не выразимо в тесте» (F6: запись в `EXCEPTIONS.md` с ID `EX-…` и сроком); якорь и срок видит Q-19.
- Режим: L4, блокирующий на найденный краш (через задачу).

### Q-15 Верификация и статус CI
- Проверяет: H6, H9.
- Критерий: (1) merge — только при зелёном CI; источник статуса — только CI; (2) утверждение о CI-покрываемой проверке («тесты проходят», «собирается») при красном CI — красный PR (механическая детекция); (3) для проверок вне конвейера — ссылка на воспроизводимый артефакт (run ID / команда + хеш вывода / перезапускаемый скрипт); упомянутые команды должны существовать в конфигурации/скриптах репозитория — бот сверяет; (4) PR-шаблон содержит чек-лист автора (единый источник — `AI_AGENT_RULES.md`) и поле «стоп-события сессии».
- Режим: процессный + автоматические подгейты (2)–(3).

### Q-16 Диф-гигиена и границы задачи
- Проверяет: H1.
- Критерий: (1) список ожидаемых файлов берётся из трекера по ID задачи в названии ветки/PR — не из описания PR; если список в задаче отсутствует, гейт не применяется (это заявлено прямо), остаётся сигнальный режим; (2) «механические изменения» — по определению в §0.7 `ENGINEERING_PRINCIPLES.md`; (3) диф > 600 строк вне механических — сигнал ревьюеру; (4) агрегаты по субъекту (число PR/подавлений/guard-меток за период) — против «салямного» размытия малыми порциями (см. `EXCEPTIONS_POLICY.md` §8).
- Режим: сигнальный + процессный.

### Q-17 Тайм-ауты и лимиты внешних взаимодействий
- Проверяет: B6, G6 (частично).
- Критерий: статические правила на известные паттерны внешних вызовов без тайм-аута/лимита (HTTP-клиент без timeout, чтение сокета/потока без лимита, БД-запрос без тайм-аута). Дефолтные значения — матрица в `ENGINEERING_PRINCIPLES.md` B6; гейт проверяет наличие явного предела, а не конкретное число. Частичная механика — полноту обеспечивает ревью.
- Инструменты: правила Semgrep/CodeQL проекта.
- Режим: К1 — блокирующий; К2 — warning.

### Q-18 Рекурсия и циклы по внешним данным
- Проверяет: A2, A3 (частично).
- Критерий: статические правила: рекурсия в модуле, обрабатывающем внешние данные, без видимого предела глубины; цикл чтения потока без явного максимума. Дефолтный предел (64) и правило переопределения — `ENGINEERING_PRINCIPLES.md` A2. Частичная механика — полноту проверяет ревью (чек-лист A2/A3).
- Инструменты: Semgrep/CodeQL, линтеры.
- Режим: К1 — блокирующий; К2 — warning.

### Q-19 Аудит исключений и классов проектов
- Проверяет: `EXCEPTIONS_POLICY.md` §6–7; `REPO_CLASS`.
- Критерий: еженедельная L4-джоба: (1) якоря `EX-…` в коде сверяются с реестром `EXCEPTIONS.md` — несовпадение (включая незарегистрированные «срочные» отступления старше 1 рабочего дня) — красный; (2) просроченные исключения — красный флаг для затронутых файлов; (3) ≥ 3 исключения одного принципа с одной причиной — автоматическая задача на PR в стандарт (E-D); (4) доля К3-кода против лимита профиля (дефолт ≤ 20% — §0.6 `ENGINEERING_PRINCIPLES.md`): ≥ 16% — алерт владельцу стандарта, выше лимита — красный; PR, меняющий одновременно код и `REPO_CLASS`, — красный (переклассификация вниз — отдельным PR, см. §0.6).
- Режим: L4; красный флаг по пунктам (1)–(2).

## 5. Механически проверяемое vs требующее суждения

| Проверяемо автоматом (гейты) | Требует инженерного суждения (ревью) |
|---|---|
| Формат, линт, типы, компиляция без предупреждений (Q-01…03) | Осмысленность контрактов и границ (D1) |
| Тесты зелёные, тайм-ауты, flaky-статистика (Q-04) | Адекватность матрицы границ (D6) |
| Покрытие дифа (Q-05) | Качество тестов: что именно проверяют (не «покрытие ради процента») |
| Санитайзеры, гонки (Q-06) | Корректность стратегии памяти (B1) |
| Секреты, CVE, lockfile (Q-07, Q-08) | Оправданность новой зависимости (E5) |
| Направления импортов, циклы (Q-09) | Разумность границ модулей, спекулятивность абстракций (E2) |
| API-диф, breaking (Q-10) | Приемлемость изменения контракта (E7) |
| Подавления vs базовая линия, EX-ID, конфиги гейтов (Q-11) | Ложность конкретного срабатывания (Q-11, часть 2) |
| Якоря EX vs реестр, просрочки, доля К3 (Q-19) | Обоснованность конкретного исключения (EXCEPTIONS_POLICY) |
| Диф эталонов требует меток/владельца (Q-12) | Корректность *нового* эталона (H8) |
| Пороги бенчмарков (Q-13) | Причина регрессии и адекватный ответ (C5) |
| Краши фаззера (Q-14) | Оценка применимости CVE к конфигурации (Q-08) |
| Тайм-ауты/лимиты: известные паттерны (Q-17) | Полнота покрытия внешних вызовов (B6) |
| Рекурсия/циклы: известные паттерны (Q-18) | Доказуемость границы в конкретном случае (A2/A3) |
| Лог верификации заполнен, CI зелёный (Q-15) | Достаточность верификации под риск задачи |
| Размер/состав дифа (Q-16) | Реальная граница задачи (H1) |

**Норма проектирования:** если правило нельзя автоматизировать, оно формулируется в чек-листе ревью одним проверяемым вопросом — и так и остаётся вопросом, а не «моральным обязательством».

## 6. Стоп-условия агента и честность принуждения

Перечень стоп-условий — единый источник: `AI_AGENT_RULES.md` §6 (дубликата здесь нет — E6 применяется к самому стандарту). Два уровня принуждения:

**Механически подкреплённые** (обход = красный гейт, «остановка» не зависит от доброй воли агента): изменение публичного API/схемы (Q-10), правка эталонов/правил (Q-12), новая зависимость (Q-08), подавления/конфигурации гейтов (Q-11).

**Процессные** (неоднозначность требований, падения тестов вне границ задачи, невозможность верификации) — контроль артефактами процесса:
- обязательное поле PR/задачи «стоп-события сессии»: перечень с маркерами `[STOP: <условие>]` или «нет»;
- артефакт остановки: статус задачи `question` + назначенный владелец + срок ответа (SLA); merge в состоянии `question` заблокирован;
- список упавших тестов и перезапусков фиксируется в PR; бот сверяет историю прогонов CI («красный → зелёный без изменения кода» — сигнал);
- критерий «обратимого предположения» — формальный: не меняет публичную поверхность/данные/эталоны (детектируется Q-10/Q-12) и не выходит за лимит файлов задачи.

**Метрика зрелости:** доля механически исполненных `[ОБЯЗ]`-правил публикуется рядом со стандартом; правила без механики явно помечены «процессное» в итоговой таблице `ENGINEERING_PRINCIPLES.md`.

**Политика при недоступном/инфраструктурно красном CI:** мердж запрещён; легитимные пути — (а) заморозка до восстановления, (б) процессное отступление с подписантом по §5 `EXCEPTIONS_POLICY.md` и обязательным отложенным полным прогоном. Админ-мердж «мимо» без записи — нарушение процесса.

## 7. Чек-лист ревью (немеханические требования)

Чек-лист автора — не дублируется здесь: он живёт в PR-шаблоне, единый источник — `AI_AGENT_RULES.md`. Обязательный минимум ревью — по одному проверяемому вопросу на правило (норма §5).

**Немеханические правила, проверяемые только человеком:**

```
[ ] Границы задачи: всё затронутое действительно нужно для задачи; попутных изменений нет (H1, Q-16)
[ ] Нет спекулятивных абстракций: у нового интерфейса — вторая реализация или тестовая подмена сейчас (E2/H2, сигнал Q-09)
[ ] Тесты проверяют поведение, а не реализацию; ослаблений и «подгонок» нет (H5, Q-12)
[ ] Предположения из задачи подтверждены владельцем; молчаливых допущений нет (H7)
[ ] Отчёт полон и честен: факты/ожидания разделены, «не проверено» названо, лог стоп-событий приложен (H9, Q-15)
[ ] Оптимизация — только по измеренной проблеме; измерение «до/после» есть (C4/C5, Q-13)
[ ] У интерфейса нет фиктивной «второй реализации» ради галочки (E2)
```

**Дополнительно (остальные немеханические правила):**

```
[ ] Контракты видны в сигнатурах/типах; граничная матрица адекватна (D1, D6)
[ ] Ошибки обрабатываются осмысленно; тайм-ауты/лимиты на всех внешних вызовах (D2, B6)
[ ] Пороги сложности превышены осознанно, с обоснованием в PR (A4)
```

## 8. Человек-ревьюер: роль, SLA, эскалация

Человек-ревьюер — обязательный контур стандарта: CI проверяет механику (§5), ревьюер — суждение; дублировать работу гейтов в ревью запрещено. Существование внимательного человеко-ревью — **явное допущение** стандарта; для агентных PR действуют дополнительные правила §1.5.3 (запрет агент-аппрува).

**SLA первого содержательного ответа на PR** (рабочие дни):

| Тип PR | SLA |
|---|---|
| Обычный | ≤ 2 дней |
| Guard-метки (`gates-change` / `rule-change` / breaking) | ≤ 1 дня |

- Молчание дольше SLA → автор эскалирует владельцу стандарта; владелец сам проводит ревью или делегирует — в течение 1 рабочего дня.
- PR без ответа дольше 5 рабочих дней — сигнал в метрики процесса (агрегатор — трек D), **не** основание мержить без ревью.
- Мердж без немеханического ревью там, где оно требуется (guard-метки, breaking, H-правила), — нарушение процесса, а не «просрочка ревьюера».
