# EXCEPTIONS_POLICY
## Политика обоснованных отступлений

**Версия:** 1.2 · **Назначение:** как легитимно отступить от требования `ENGINEERING_PRINCIPLES.md`, не разрушив стандарт. Отступление — управляемая и видимая форма долга, а не «обход конвейера».

---

## 1. Основной принцип

Стандарт ценен тем, что исполняется автоматически. Каждое исключение — локальное ослабление гарантии, поэтому оно должно быть: **точечным** (минимальный охват), **обоснованным** (записанная причина), **ограниченным во времени** (срок пересмотра), **одобренным** (подписант по уровню риска) и **видимым** (обнаруживается автоматикой, считается в метриках).

Запрещено ослаблять правило изменением его глобальной настройки — глобальные изменения стандарта идут через изменение самого стандарта (раздел 6), а не через исключение.

## 2. Виды отступлений

| Вид | Что это | Где живёт | Срок |
|---|---|---|---|
| **E-A. Точечное подавление** | Отключение конкретного срабатывания инструмента в конкретной строке | Прямо в коде: `# noqa: E501 # причина: длинная таблица данных` (без EX-ID; учитывается гейтом Q-11 против базовой линии) | Пересмотр — при ревью файла или по алерту Q-11 |
| **E-B. Временная базовая линия** | Признанные существующие нарушения легаси | Файл-базовая линия (ratchet-конфиг) | Снижается по плану; конкретный срок в плане внедрения |
| **E-C. Отступление по требованию** | Осознанное нарушение принципа ради конкретной цели (совместимость, производительность измеренная, ограничения платформы) | Запись в `EXCEPTIONS.md` репозитория + якорь в коде (`EX-…`) | С фиксированным сроком пересмотра (по умолчанию ≤ 6 месяцев) |
| **E-D. Изменение стандарта** | Правило плохо применимо к классу задач в принципе | PR в настоящий стандарт | Постоянно |

Не путать: **любая ошибка линтера/теста** не становится исключением автоматически — сначала доказывается ложность срабатывания или легитимность нарушения (раздел 4).

## 3. Регистрация исключения (форма)

Каждое E-C исключение получает ID `EX-<год>-<NNN>` и запись:

```markdown
### EX-2026-001
- **Принцип:** B6 (лимиты внешних взаимодействий)
- **Область:** `services/legacy-bridge/recv.py`, функция `recv_loop`
- **Суть отступления:** отсутствие лимита числа сообщений, гарантия задана протоколом v1 (пировое соединение с собственным лимитом)
- **Обоснование:** изменение протокольной прослойки = проект вне спринта; риск ограничен внутренней сетью
- **Компенсирующие меры:** watchdog по времени ответа, алерт на рост очереди
- **Подписант:** tech lead (см. раздел 5)
- **Срок пересмотра:** 2026-06-01
- **Статус:** активное
```

Анкер в коде обязан ссылаться на ID:

```python
# EX-2026-001: см. EXCEPTIONS.md — лимит сообщений задан протоколом v1
```

## 4. Порядок принятия решения

### 4.1. Алгоритм для агента/разработчика

1. **Диагностика.** Нарушение реально? Или срабатывание ложно?
   - Ложное срабатывание → E-A (точечное подавление с причиной). Глобальная правка конфигурации инструмента — не E-A (см. 4.3).
   - Реальное нарушение → шаг 2.
2. **Альтернативы.** Есть ли исполнимый способ соответствовать правилу в разумный срок? Если есть — делай соответствие, не исключение.
3. **Оценка риска.** Какие гарантии ослабляются? Каков компенсирующий контроль?
4. **Регистрация.** Форма раздела 3, якорь в коде, метка PR `exception`.
5. **Одобрение** подписантом (раздел 5).
6. **Пересмотр** по сроку: исключение либо закрывается (соответствие), либо продлевается с новой записью обоснования. Молчаливое продление запрещено.

### 4.2. Кто подтверждает ложное срабатывание инструмента

Ложность срабатывания подтверждается кодом-минимумом или ссылкой на документацию правила — не «мнением». Если срабатывание спорно, это нарушение по умолчанию (F2: «исправляй код, а не предупреждение» — перепиши код так, чтобы вопрос исчез).

### 4.3. Что не является исключением

- Изменение конфигурации гейтов/линтеров **ради прохождения конкретного PR** — запрещено всегда. Легитимное изменение конфигурации существует только как E-D (изменение самого стандарта): отдельный PR с обсуждением и подписантами §5 — это правка стандарта, а не исключение.
- Ослабление или удаление тестов под текущий код без доказательства дефектности теста (H5) — не исключение, а нарушение.
- Фикция результата верификации (H6) — не исключение, а нарушение с установленными последствиями (§8).
- Сканеры секретов (Q-07): исключений нет; протечка = немедленная ротация + санация истории.
- Ручная правка отчётов CI, подделка артефактов — нарушение, не исключение.

### 4.4. Срочные отступления (инциденты)

При активном инциденте допускается отступление «сначала действие»: якорь + черновик записи в исключения в том же PR; полная регистрация и подписант — в течение **1 рабочего дня**. Незарегистрированное отступление старше 1 рабочего дня автоматически становится красным флагом (Q-19 сверяет якоря `EX-…` с реестром).

## 5. Уровни подписантов

| Риск отступления | Подписант | Примеры |
|---|---|---|
| Низкий: локальный, обратимый, без контрактов/данных | Автор + ревьюер PR | E-A подавление линтера в тесте |
| Средний: затрагивает надёжность/производительность модуля | Tech lead владельца модуля | E-C на B6/G6 для внутреннего сервиса |
| Высокий: публичные контракты, данные, безопасность, деньги | Архитектор + владелец домена | E-C на E7 (breaking), G-класс правил, расчётные формулы |
| Гейт-конфигурации (изменение порогов/набора гейтов) | Владелец стандарта + tech lead | Снижение порога Q-05 |

## 6. Изменение самого стандарта

Если правило систематически нарушается по одинаковому обоснованию — это сигнал не «раздать исключения», а проверить правило:

1. Q-19 автоматически детектирует ≥ 3 исключения E-C одного принципа с одинаковой причиной и создаёт задачу.
2. Владелец стандарта обязан открыть PR в стандарт: уточнить применимость, добавить явное условное правило либо перенести в [РЕК]/[УСЛ].
3. Решение фиксируется в `CHANGELOG.md` (единая история версий стандарта).

## 7. Видимость и метрики исключений

- `EXCEPTIONS.md` репозитория — единственный реестр E-C; просроченные исключения подсвечиваются автоматикой (проверка дат — L4).
- Подписант не может быть автором изменения — разделение ролей обязательно для уровней «средний» и «высокий» (см. §5).
- Метрики на дашборд: число активных исключений; распределение по принципам и модулям; скорость закрытия.
- **Норма здоровья:** рост активных исключений в модуле — красный флаг ревью архитектуры. Концентрация исключений одного принципа — кандидат в изменение стандарта (раздел 6).
- Подсчёт подавлений (E-A) — гейтом Q-11; их рост сверх базовой линии — сигнал.
- Метрики интерпретируются совместно: «низкая доля меток exception при высоком числе подавлений» — красный флаг, а не здоровье (закон Гудхарта: целевая метрика перестаёт измерять то, ради чего введена).

## 8. Реакция на нарушения (не оформленные как исключения)

Исключения — управляемый долг; нарушения без исключения — саботаж конвейера. Классификация и последствия:

- **Непреднамеренное** (незнание): ревью возвращает на доработку; повторность — сигнал обновить L1-инструкции/обучение.
- **Систематическое** (повторные нарушения одного типа одним субъектом): метрика на субъекта (агент/человек); порог эскалации (по умолчанию: 3 подтверждённых нарушения домена H за квартал) — понижение автономности: агенту — режим «только draft PR» и запрет самостоятельного мержа, человеку — обязательное парное ревью.
- **Фикция верификации (H6)** — приравнена к саботажу: обязательная ретроспектива, немедленное понижение автономности до разбора, метрика рецидива на дашборде рядом с метриками исключений.

Метрики на субъектов (число PR, подавлений, guard-меток, повторных нарушений за период) агрегируются против «салямного» размытия малыми порциями.
