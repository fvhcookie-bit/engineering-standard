# IMPLEMENTATION_GUIDE
## Внедрение стандарта в существующий репозиторий

**Версия:** 1.1 · **Назначение:** практический порядок внедрения `ENGINEERING_PRINCIPLES.md` в живой проект без «большого взрыва».

---

## 0. Главный принцип внедрения

Стандарт внедряется **через гейты, а не через кампанию дисциплины**. Порядок всегда один: измерить → зафиксировать базовую линию → запретить рост → снижать базовую линию постепенно. Попытка «исправить всё сразу» производит тысячи коммитов без ревью-ценности и саботирует доверие к конвейеру.

## 1. Этапы внедрения

### Этап 1. Классификация (1 день)
- Присвой репозиторию класс К1/К2/К3 (`ENGINEERING_PRINCIPLES.md` §0.6); при неоднородности — классы модулям.
- Создай `REPO_CLASS`: классы репозитория/модулей, версия стандарта, ссылка на манифест критичных модулей — под CODEOWNERS владельца стандарта.
- Назначь владельца стандарта в репозитории (тот, кто подписывает исключения и конфигурации гейтов).

### Этап 2. Снимок базовой линии (1–3 дня)
- Запусти полный набор инструментов в режиме «только отчёт»: формат-диф, линтер, типы, статический анализ, аудит зависимостей, скан секретов, метрики сложности, покрытие.
- Зафиксируй результаты в ratchet-конфиге (см. `QUALITY_GATES.md` §3). Это точка отсчёта — не приговор.
- Отдельно: скан секретов **не** входит в храповик — находки исправляются немедленно (ротация + санация истории).
- Файлы базовой линии — под CODEOWNERS владельца стандарта; сброс baseline — отдельным PR с меткой `baseline-reset`.

### Этап 3. Минимальный рабочий конвейер (2–5 дней)
Включи в CI блокирующие гейты, которые дёшево стоят и почти не дают ложных срабатываний:
1. Formatter + линтер по дифу (только новые срабатывания).
2. Типы (строгий режим на новых модулях; на существующих — по храповику).
3. Юнит-тесты + тайм-ауты.
4. Скан секретов (полный, блокирующий, без исключений).
5. Аудит CVE (блокирующий для критичных).
6. PR-шаблон с чек-листом автора, полем «стоп-события сессии» и правилами верификации (Q-15).

**Сначала L0.** Выполни `QUALITY_GATES.md` §1.5: branch protection, запрет force-push, обязательные проверки, CODEOWNERS на инфраструктуру стандарта, запрет агент-аппрува. **Без L0 стандарт не считается внедрённым** — весь L3 отключается галочкой в настройках хостинга.

**Про pre-commit.** L2 обязателен для К1/К2, конфиг хуков — в репозитории. Обход через `--no-verify` локально не пресечь, поэтому всё критичное из L2 дублируется в L3: конвейер не зависит от локальных хуков. Агенту запрещено использовать `--no-verify` без явного разрешения в задаче.

**Про guard-гейты.** Q-10…Q-12, Q-19 — кастомные CI-скрипты, готовых инструментов под них нет; используй companion-репозиторий стандарта (реализации гейтов + строгие профили конфигураций по языкам) либо закладывай ресурс на их написание — это слой, на котором внедрение обычно буксует.

### Этап 4. Инструкции для агентов и людей (1 день)
- `AGENTS.md` (или эквивалент) в корне: ссылка на `AI_AGENT_RULES.md` + стоп-условия + ссылка на `EXCEPTIONS_POLICY.md`.
- Шаблон задачи с полем «Предположения».
- Раздел в `CONTRIBUTING.md`: краткий порядок исключений и ссылка на гейты.

### Этап 5. Архитектурные и контрактные гейты (1–2 недели, по готовности)
- Зафиксируй текущие направления зависимостей в `ARCHITECTURE.md` (сначала опиши то, что есть, а не то, что «правильно»).
- Включи арх-тесты (Q-09) в режиме «запрет роста»: новые циклы/направления запрещены, существующие — в базовой линии.
- Для библиотек/платформ — api-diff (Q-10) и guard-гейты (Q-11, Q-12).

### Этап 6. Снижение базовой линии (постоянно)
- Каждому принципу с большим долгом — «хозяин» и целевой уровень с датой.
- Порядок снижения по ROI: (1) ошибка глотания/игнора, (2) тайм-ауты/лимиты на внешних вызовах, (3) рекурсия по внешним данным, (4) необработанные ошибки, (5) покрытие критичных модулей тестами, (6) остальное.
- Пороговые метрики (A4): абсолютные пороги — warning; храповик на изменённых функциях — blocking с чекбоксом-обоснованием (Q-02).

### Этап 7. Производительность, фаззинг и мутации (при наличии бюджетов/парсеров)
- Определи бюджетные пути (B5), добавь бенчмарки (Q-13) и цели фаззинга (Q-14): перечень целей (парсеры, декодеры протоколов, обработчики форматов) фиксируется в репозитории.
- Для К1 и критичных модулей — ночные спот-чеки мутационного тестирования (mutmut/Stryker/PIT/cargo-mutants) — механическая проверка силы тестов.
- Без бюджетов — не начинай (иначе шум алертов убьёт доверие).

## 2. Матрица инструментов (стартовые наборы по языкам)

| Язык | Формат | Линт/типы | Анализ/санитайзеры | Тесты | Безопасность |
|---|---|---|---|---|---|
| C | clang-format | clang-tidy, cppcheck | ASan/UBSan/TSan, CodeQL | Unity/CMock, Criterion | gitleaks, osv |
| C++ | clang-format | clang-tidy, cppcheck | ASan/UBSan/TSan, CodeQL | GoogleTest/Catch2 | gitleaks, osv |
| Go | gofmt | golangci-lint, vet | `go test -race` | testing, testify | gitleaks, govulncheck |
| Java/Kotlin | ktlint/google-java-format | detekt, ErrorProne, SpotBugs | Infer, CodeQL | JUnit5, MockK | gitleaks, OWASP DC |
| JS/TS | prettier | eslint+types, tsc strict | Semgrep/CodeQL | vitest/jest, playwright | gitleaks, npm audit |
| Python | ruff format | ruff, mypy strict | Semgrep, bandit | pytest, hypothesis | gitleaks, pip-audit |
| Rust | rustfmt | clippy (strict) | miri/asan, cargo-fuzz | cargo test, proptest | gitleaks, cargo audit |
| C# | dotnet format | analyzers (strict), Roslyn | Roslyn analyzers + Semgrep/SonarQube в CI | xUnit/NUnit | gitleaks, osv |

Архитектурные тесты: ArchUnit (JVM), dependency-cruiser / import-linter (JS/TS/Py), eslint-plugin-boundaries; для Go — кастомные скрипты по списку пакетов (готового инструмента нет). Для К1/К2 дополнительно: SBOM (syft/cyclonedx) в релизном конвейере; api-diff — инструменты экосистемы из таблицы.
Фаззинг: libFuzzer/AFL++ (C/C++), go-fuzz/stdlib fuzzing, cargo-fuzz, AFL-совместимые обёртки для других языков.
Заметка: приведены примеры, не предписания; правило одно — инструмент включается гейтом из каталога, а не «в потолок».

## 3. Внедрение в агентных workflow

- L1-инструкции (`AGENTS.md`) держи короткими: правила — в `AI_AGENT_RULES.md`, исполнение — в CI. Агент, читающий 200-строчный регламент, исполняет его хуже, чем агент, у которого 40 строк правил и жёсткий конвейер.
- Дай агенту доступ к запуску гейтов локально (make/scripts) — тогда H6/H9 исполняются реально.
- Guard-гейты (Q-11, Q-12) обязательны для репозиториев с агентными PR: они превращают «не ослабляй проверки» и «не трогай эталоны» из инструкции в механику.
- Остановки агента (стоп-условия) формализованы артефактом: статус задачи `question` + владелец + срок; маркеры `[STOP: …]`; лог стоп-событий — обязательное поле отчёта (`QUALITY_GATES.md` §6).
- Canary-проверка: включи в `AGENTS.md` 1–2 проверяемых поведенческих маркера (например, обязательный формат отчёта H9) — бот отклоняет PR без них; это дешёвая детекция «агент не читал L1».
- Коммиты агента — с трейлером `AI-Origin: <агент/модель>`: аудит инцидентов, метрики по субъектам, запрет агент-аппрува.

## 4. Метрики успеха внедрения

- Время до зелёного CI на PR (цель: < 15 минут юнит-уровень).
- Число нарушений базовой линии (монотонно убывает; график виден команде).
- Доля PR с метками `exception`/`gates-change`/`rule-change` (низкая и не растёт).
- Найденные на гейтах дефекты до merge (полезность конвейера — считать и показывать).
- Flaky-доля тестов (цель: < 1%).
- Метрики против закона Гудхарта: «доля PR с метками» интерпретируется только вместе с абсолютами (число подавлений по Q-11, результаты Q-19); «низкая доля меток при высоком числе подавлений» — красный флаг.
- CI медленнее 15 минут — инцидент конвейера: профилирование пайплайна, шардирование, кеширование; медленный CI — главный драйвер саботажа гейтов.
- Доля механически исполненных [ОБЯЗ]-правил — публикуемая метрика зрелости стандарта.

## 5. Приоритезированный список внедрения (сводка)

1. **Секреты и CVE-гейты** (Q-07, Q-08) — дёшево, огромный риск, ноль спорных срабатываний.
2. **Формат + линт + типы по дифу** (Q-01…03) — фундамент храповика.
3. **PR-шаблон с логом верификации и предположениями** (Q-15, H7/H6/H9) — дисциплина агентов без кода.
4. **Тесты + тайм-ауты + диф-покрытие** (Q-04, Q-05).
5. **Guard-гейты** (Q-11, Q-12) — защита конвейера от агентов и дедлайнов.
6. **Архитектурные тесты** (Q-09) — после фиксации фактической архитектуры.
7. **api-diff** (Q-10) — для библиотек/платформ.
8. **Бенчмарки и фаззинг** (Q-13, Q-14) — только при наличии бюджетов/парсеров.
9. **Снижение долга** по ROI-порядку этапа 6.
10. **Изменение стандарта по сигналам исключений** (EXCEPTIONS_POLICY §6) — постоянный цикл.

## 6. Анти-паттерны внедрения

- «Включить всё строго сразу» → шторм красного CI → отключение гейтов → доверие утрачено.
- «Покрытие 100% как гейт» → тесты-фантики, замедление конвейера.
- «Функции ≤ 60 строк как блокирующий гейт» → механическое дробление (A4).
- «Правила только в промпте агента» → исполнение зависит от настроения модели.
- «Базовую линию обновляем по пятницам, чтобы CI был зелёным» → храповик превращён в лифт.
- «Исключения оформляем устно в чате» → невидимый долг: а протокол не ведётся.
- «Конвейер стал медленным — перенесём проверки на ночь» → обратная связь рвётся, гейты начинают обходить; скорость конвейера — часть стандарта (§4).

## 7. Откат и аварийные режимы

- Отключение/ослабление гейта — только через E-D: PR в конфигурацию с меткой `gates-change`, подписант — владелец стандарта, срок не более одного цикла, с записанной причиной.
- Аварийный режим (инцидент продакшна): процессное отступление с подписантом по `EXCEPTIONS_POLICY.md` §5 + обязательный отложенный полный прогон + ретроспектива.
- Недоступный/красный по инфраструктурным причинам CI: мердж запрещён; пути — заморозка либо аварийный режим (см. выше).
- Откат внедрения (команда перегружена): снижайте строгость только через E-D, по одному гейту, с измерением эффекта — не «выключаем всё».
