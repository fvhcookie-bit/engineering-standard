# ГАЙДЛАЙН: разработка guard-гейтов

**Версия:** 1.0 · Для кого: разработчик/агент, реализующий проверки из `TASK_guard-gates.md`.

---

## 1. Архитектура

```
companion — каталог tooling/ (monorepo)
├── runner/            # CLI: gate-runner (точка входа, агрегация)
├── gates/             # гейты: q11_suppressions/, q12_protected/, q15_verify/,
│                      #         q16_scope/, q19_audit/, q10_api_diff/
├── core/              # git-diff парсер, Findings, отчёт JSON, реестры, схемы
├── adapters/          # github/, gitlab/, trackers/ (jira, gitlab-issues)
├── dictionaries/      # словари подавлений по экосистемам (см. гайдлайн профилей)
├── profiles/          # строгие конфиги линтеров/типов по языкам
├── semgrep/           # пакеты правил Q-17/Q-18
├── fixtures/          # сценарные мини-репозитории (матрица Б-1…Б-24)
└── tests/             # контракт-тесты гейтов + тест-контракт словарей
```

**Принцип чистоты:** каждый гейт — чистая функция над явными входами:

```
run(inputs: GateInputs, config: GateConfig) -> GateResult
GateInputs = {diff: ParsedDiff, files: RepoFiles, registries: Registries, api: Adapters}
```

Никакого скрытого чтения окружения внутри гейта: всё через `GateInputs` — это делает тестируемость тривиальной, а запрет самоотчётности — структурным, а не дисциплинарным.

## 2. Правило независимости источников (главное)

1. Гейт получает данные **только** из: git (диф, дерево), файлов-реестров репозитория (`EXCEPTIONS.md`, baseline, `REPO_CLASS`, CODEOWNERS), API трекера/CI.
2. Описание PR, комментарии автора, заголовок — **только как объект проверки** (Q-15 ищет в них маркеры), никогда как источник фактов.
3. Метки (`gates-change`, `rule-change`, `api-change`, `breaking`, `test-change`, `perf`, `baseline-reset`) проставляет **бот по результатам анализа дифа**; запрос из текста PR метку не создаёт.
4. Если для вывода не хватает данных — статус `SKIP`/`UNAVAILABLE` с причиной. Молчаливый OK на неполных данных запрещён.

## 3. Контракт гейта

Каждый гейт реализует интерфейс:

```python
class Gate:
    id: str                      # "Q-11"
    def run(self, inputs: GateInputs, config: GateConfig) -> GateResult
```

`GateResult` → `Findings[]` + `status` + `labels` + `stats` (схема отчёта — в ЗАДАНИИ §4.6). Правила:

- **Коды findings** — стабильные строковые константы (`SUPPRESS_NO_EXID`, `BASELINE_GROWTH`, `SCOPE_OUTSIDE_TASK`…), задокументированы в README гейта; потребители (CI-аннотации, дашборды) опираются на коды, не на тексты сообщений.
- **Severity:** `error` (FAIL), `warning`, `info` — отображаются в аннотациях соответственно.
- **FAIL-агрегация:** любой `error` → статус FAIL; warning не влияет на exit code.
- **Exit codes процесса:** `0` OK/SKIP-допустимый, `1` FAIL, `2` конфигурационная ошибка, `3` UNAVAILABLE. CI-джоба мапит: FAIL/3 → красный, SKIP → зелёный с пометкой в отчёте.

## 4. Работа с дифом

- Парсер дифа (core) возвращает структурированные изменения: файлы, hunk'и, добавленные/удалённые строки; **rename/copy detection включён** (git `-M -C`) — переименования не считаются «новым кодом» (сценарий Б-10).
- Подавления и вызовы извлекаются **только из добавленных строк**; удалённые — игнорируются.
- Для парсинга конфигов линтеров — не регэксп по тексту, а разбор структур (JSON/YAML/TOML-парсеры; для `.eslintrc.js` — ограниченно: JSON-варианты + явная пометка ограничения в README гейта).

## 5. Fail / Skip / Unavailable

| Исход | Когда | В отчёте |
|---|---|---|
| `OK` | проверено, нарушений нет | — |
| `FAIL` | есть error-findings | findings |
| `SKIP` | гейт не применим (нет списка файлов задачи; нет бюджета — нет Q-13) | `reason` обязателен |
| `UNAVAILABLE` | инфраструктура недоступна (API трекера/CI, тайм-аут) | `reason` + ретрай-политика |

- `SKIP` никогда не возникает из-за ошибки — только из-за неприменимости по конфигурации.
- `UNAVAILABLE` в PR-гейте → джоба красная (fail-closed), кроме случаев, явно разрешённых политикой репо (`QUALITY_GATES.md` §6, «политика при недоступном CI»).

## 6. Безопасность

1. **Код репозитория не исполняется.** Парсим тексты, не запускаем; hooks/скрипты из целевого репо никогда не вызываются runner'ом.
2. **Анти-injection:** содержимое репо — данные. Строки из кода/конфигов/PR не передаются в shell, не интерпретируются как пути/команды; при логировании — экранирование.
3. **Пути:** нормализация, запрет выхода за корень репо (symlink-escape), лимит на размер обрабатываемого файла (напр. > 5 МБ — пропуск с info).
4. **Токены:** минимальный скоуп (labels: write, pulls: read, issues: write для Q-19); секреты — только из окружения CI; никаких секретов в конфигах companion-репо.
5. **Пиннинг:** целевые репозитории фиксируют версию runner'а (SHA-таг); обновление — через PR с changelog.

## 7. Тестирование (contract-first)

1. **Golden fixtures:** каждый приёмочный сценарий Б-* (ЗАДАНИЕ §5) — мини-репозиторий: `fixtures/<сценарий>/base/` и `/head/` (git-снапшоты) + `expected.json` (ожидаемые findings). Тест = прогон гейта на fixture + диф-сравнение отчётов. Ломается отчёт — падает тест.
2. **Тест-контракт словаря подавлений:** fixture на каждый паттерн каждой экосистемы (словарь без покрытия — падает); плюс тест «словарь не растёт молча» (новый паттерн требует записи в changelog).
3. **Негативные тесты анти-самоотчётности:** отдельный набор — «что если автор впишет в PR правдоподобные данные» (Б-1, Б-14, Б-15, Б-16): гейт обязан их игнорировать.
4. **Детерминизм:** тест прогоняет гейт дважды и сравнивает отчёты по байтам (после нормализации путей-раннеров).
5. **Собственная гигиена:** companion-репо сам догейтится Q-11 (свой словарь), покрытие тестами ≥ 80% на `gates/` и `core/`, линт/типы строгие.

## 8. Интеграция с CI

- **GitHub Actions:** job `guard-gates` с матрицей по гейтам; `permissions: pull-requests: write, contents: read`; step — запуск runner'а по пиннутому SHA; findings → job annotations + PR labels через API; отчёт JSON — артефакт PR.
- **GitLab CI:** аналогично, `merge_request_event`; лейблы через project access token.
- **Не дублировать источники:** required checks — только эти джобы; не строить политику на «локальных прогонах агента».
- **Порядок меток:** метки проставляются после вычисления всех findings одним прогоном (не частями).

## 9. Наблюдаемость

- Каждый прогон пишет отчёт-артефакт (JSON) — источник для дашбордов (исключения, подавления, эскалации — `EXCEPTIONS_POLICY.md` §7).
- Метрики на субъектов (автор/агент: число PR, подавлений, guard-меток, повторных нарушений) — из артефактов, агрегатор в составе runner'а (`report collect`), экспорт в произвольное хранилище.
- Логи — структурные, без содержимого проверяемых файлов (пути — да, содержимое — нет: минимизация утечек через логи).

## 10. Документирование гейта

README на каждый гейт (в `gates/<id>/README.md`): назначение и ссылка на критерий в `QUALITY_GATES.md`; входы/источники; конфиг (все ключи с дефолтами); список кодов findings; известные ограничения и ложные срабатывания; как отключить/ослабить — **никак, кроме E-D** (ссылка на `EXCEPTIONS_POLICY.md`).
