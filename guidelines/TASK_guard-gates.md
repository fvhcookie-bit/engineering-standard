# ЗАДАНИЕ: реализация guard-гейтов стандарта (companion-репозиторий)

**Версия:** 1.0 · **Основание:** `../standards/QUALITY_GATES.md` v1.1 (каталог гейтов), `../standards/ENGINEERING_PRINCIPLES.md` v1.1
**Стек реализации по умолчанию:** Python 3.11+ (минимум зависимостей: PyYAML, requests/urllib3); допустим Go — по согласованию с владельцем стандарта.

---

## 1. Цель и объём

Создать набор детерминированных CI-скриптов, исполняющих guard-гейты стандарта в целевых репозиториях. Гейты работают с **независимыми источниками данных** (git, реестры репозитория, API трекера/CI) и никогда — с декларациями автора PR.

**Входит в объём:**

| Пакет | Гейты | Приоритет |
|---|---|---|
| Каркас runner + контракт отчёта + тестовая инфраструктура | — | M1, блокер |
| Подавления и конфигурации гейтов | Q-11 | M2, блокер |
| Аудит исключений и классов | Q-19 | M2, блокер |
| Эталоны и правила (защищённые пути) | Q-12 | M3 |
| Верификация и статус CI | Q-15 | M3 |
| Границы задачи (диф-гигиена) | Q-16 | M3 |
| Обёртки api-diff | Q-10 | M4 |
| Пакеты правил Semgrep/CodeQL | Q-17, Q-18 | M4 |
| Строгие профили конфигов и словари по языкам | Q-01/Q-02/Q-03 | M4, далее постоянно |

**Не входит в объём:** Q-01…Q-09 как таковые (это обёртки над готовыми инструментами, собираются из профилей), переписывание инструментов, автоматические исправления (гейты только детектируют и сообщают), автоматический мердж.

## 2. Референсная модель окружения целевого репозитория

Скрипты вправе полагаться на наличие (см. `QUALITY_GATES.md` §1.5, L0):

- `EXCEPTIONS.md` в корне — реестр исключений E-C: блоки `### EX-ГГГГ-NNN` с полями «Принцип», «Область», «Суть отступления», «Обоснование», «Компенсирующие меры», «Подписант», «Срок пересмотра» (дата), «Статус»;
- `baseline/suppressions.yaml` — базовая линия подавлений (формат см. GUIDELINE_profiles_and_dictionaries §1);
- `REPO_CLASS` — классы репозитория/модулей, версия стандарта, ссылка на манифест критичных модулей;
- манифест критичных модулей и список защищённых путей (golden-файлы, модули формул) — в конфиге гейтов;
- CODEOWNERS на все перечисленные файлы.

## 3. Требования по гейтам

### 3.1. Q-11 «Подавления и конфигурации гейтов» (блокер)

**Вход:** git-диф `base…head`, `baseline/suppressions.yaml`, `EXCEPTIONS.md`, словарь подавлений (по экосистемам), парсеры эффективных конфигураций линтеров.
**Логика:**
1. Извлечь из дифа подавления (только добавленные строки; удалённые — не считаются) по словарю паттернов.
2. Для каждого нового подавления: наличие комментария-причины; валидный ID `EX-…` из реестра; срок пересмотра не истёк. Отсутствие/просрочка — FAIL.
3. Сравнить число подавлений (по видам) с базовой линией: рост — FAIL. **Компенсации запрещены** («+3 новых / −4 старых» — FAIL).
4. Более 3 подавлений на PR → требование второго ревьюера (метка + `mergeable=false` до аппрува из CODEOWNERS).
5. Диф **эффективной** конфигурации инструментов (распарсенный канонический JSON, а не текст конфига) или появление нового конфиг-файла инструмента в дереве (включая вложенные каталоги) → принудительная метка `gates-change`.
6. PR трогает и baseline-файлы, и код → FAIL (`baseline-reset` — только отдельный PR).
7. Удаление строк с подавлениями НЕ уменьшает baseline автоматически: миграция baseline — только инструментом (`gate-runner baseline migrate`) на механических PR.

**Приёмочные сценарии:** Б-1, Б-2, Б-3, Б-5, Б-6, Б-7, Б-8, Б-10 (раздел 5).

### 3.2. Q-19 «Аудит исключений и классов» (блокер, ночной)

**Вход:** всё дерево репозитория, `EXCEPTIONS.md`, `REPO_CLASS`, даты из CI.
**Логика:**
1. Собрать якоря `EX-\d{4}-\d{3}` в коде/конфигах; сверить с реестром: якорь без записи или запись без якоря → FAIL (якорь старше 1 рабочего дня без записи — FAIL безусловно).
2. Просроченные «Сроки пересмотра» → FAIL для затронутых файлов (в PR) и запись в ночной отчёт.
3. Группировка E-C по (принцип, причина): ≥3 совпадений → автосоздание задачи «PR в стандарт (E-D)» через API трекера, с шаблоном алерта.
4. Доля К3-кода (по `REPO_CLASS`) и её изменение к прошлому прогону → алерт владельцу стандарта.

**Приёмочные сценарии:** Б-3, Б-17, Б-18, Б-19, Б-20.

### 3.3. Q-12 «Эталоны и правила»

**Вход:** диф, конфиг защищённых путей (источники: CODEOWNERS + `REPO_CLASS`).
**Логика:** диф задевает защищённый путь → метка `rule-change` + обязательный ревьюер из CODEOWNERS; пересечение с Q-11 → обе метки + наивысший подписант; **новый** golden/snapshot-файл в том же PR, где меняется код его модуля → усиленное ревью (флаг); для К1 — семантический сигнал: изменение числовых литералов в модулях из «расчётного» списка → warning-аннотация.

**Приёмочные сценарии:** Б-9, Б-11, Б-12 (пересечение меток).

### 3.4. Q-15 «Верификация и статус CI»

**Вход:** текст PR (только как объект проверки, не как источник истины), статусы required checks (API CI), упомянутые в PR ссылки на прогоны/артефакты, список команд из скриптов/конфигов репо.
**Логика:**
1. Текстовые маркеры успеха («тесты проходят», «сборка ок» и словарь маркеров из конфига) при красном required check → FAIL.
2. Ссылки на прогоны/артефакты: должны существовать в API CI и принадлежать этому коммиту/PR → иначе FAIL.
3. Упомянутые команды верификации должны существовать в скриптах/конфигурации репозитория → иначе FAIL.
4. Поле «стоп-события сессии» отсутствует в PR-шаблоне заполнения → warning (не FAIL: заполнение шаблона — процессное).

**Приёмочные сценарии:** Б-15, Б-16.

### 3.5. Q-16 «Границы задачи»

**Вход:** task ID из имени ветки/заголовка PR, файловый список задачи (API трекера), диф, конфиг «механических изменений».
**Логика:**
1. Список файлов задачи не найден в трекере → статус **SKIP** (явно в отчёте, не тихий пропуск).
2. Затронутые файлы ⊆ списку задачи → OK; вне списка → FAIL (метка `scope-violation`).
3. Диф > 600 строк вне механических изменений (определение — `ENGINEERING_PRINCIPLES.md` §0.7) → warning-аннотация.
4. Агрегаты по субъекту (PR/подавления/guard-метки за период) → при превышении порога — задача на эскалацию (см. `EXCEPTIONS_POLICY.md` §8).

**Приёмочные сценарии:** Б-13, Б-14.

### 3.6. Q-10 «api-diff» (обёртка)

**Вход:** base/head, конфиг инструментов по языкам (api-diff, rustdoc-json, oasdiff, protobuf-детекторы).
**Логика:** запуск инструмента; findings от инструмента → метки `api-change`/`breaking` (проставляет бот); для языка без инструмента → статус **UNAVAILABLE** (не молчаливый OK).

**Приёмочные сценарии:** Б-21.

### 3.7. Q-17/Q-18 — пакеты правил (не код, а правила + тесты)

Наборы правил Semgrep/CodeQL по языкам:
- **Q-17:** HTTP-клиент без `timeout`, чтение сокета/потока без лимита, БД-запрос без тайм-аута (минимум 8–12 правил на основной язык).
- **Q-18:** рекурсия в модуле обработки внешних данных без явного предела глубины; цикл чтения потока без счётчика-максимума (минимум 4–6 правил).

Каждое правило — с positive/negative fixture. Режим: К1 — блокирующий; К2 — warning (настраивается в профиле).

## 4. Нефункциональные требования

1. **Детерминизм:** два прогона на одном коммите дают идентичные отчёты (без меток времени в сравниваемых полях).
2. **Режимы исхода:** `OK | FAIL | SKIP | UNAVAILABLE` — явные; SKIP/UNAVAILABLE фиксируются в отчёте с причиной. Fail-closed для security-гейтов (Q-07-смежные пути), fail-explicit для остальных: недоступность API трекера/CI — `UNAVAILABLE`, никогда не молчаливый OK.
3. **Производительность:** PR-гейты ≤ 60 с на репозиторий ≤ 100k файлов; Q-19 ≤ 15 мин (ночной). Диф-ориентированность, без полного реанализа.
4. **Безопасность:** скрипты не исполняют код целевого репозитория (только парсят); содержимое репо трактуется как данные (анти-injection: строки из кода/конфигов никогда не интерпретируются как команды или пути исполнения); проверка путей против symlink-escape; токены CI — минимального скоупа (PR labels + чтение).
5. **Версионирование:** runner и гейты версионируются, целевые репозитории пиннят версию (лучше SHA); формат baseline и отчёта — со схемой `schema: N`.
6. **Отчёт:** машиночитаемый JSON (схема ниже) + человекочитаемые аннотации; JSON-схема версионируется.

```json
{
  "schema": 1,
  "gate": "Q-11",
  "gate_version": "1.0.0",
  "status": "FAIL | OK | SKIP | UNAVAILABLE",
  "reason": "строка для SKIP/UNAVAILABLE",
  "findings": [
    {"code": "SUPPRESS_NO_EXID", "severity": "error",
     "path": "src/x.py", "line": 42, "message": "…", "evidence": "…"}
  ],
  "labels": ["gates-change"],
  "second_reviewer_required": false,
  "stats": {"suppressions_new": 4, "baseline_total": 57}
}
```

7. **Соблюдение собственного стандарта:** companion-репозиторий — класс К2; на него распространяются все гейты, включая собственный Q-11 (сам догейтится своим же словарём).
